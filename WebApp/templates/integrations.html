1. SNMP — Printers, Switches, Access Points, IP Phones, Cameras, Firewalls {% if status.Snmp.Configured %}Configured{% else %}Not configured{% endif %}

These devices already appear in the Discovery scan as generic NetworkDevice/Unknown entries (SNMP or Telnet port responded). SNMP polling turns that into model, firmware version, and uptime/status detail.

Request from the Network/Infrastructure team:

  • A read-only SNMP community string (v2c) — or preferably per-device SNMPv3 credentials (authenticated + encrypted, since v2c community strings travel in cleartext)
  • Confirmation that SNMP is actually enabled on the target device classes — many orgs disable it by default for security
  • A firewall/ACL allow rule: UDP/161 from the jump server IP to the management subnet(s) of these devices
  • The list of subnets/VLANs these devices live on (often a separate management VLAN from user/server subnets)

Once provided, set Integrations.Snmp in settings.psd1 and set Enabled = $true.

2. Vendor warranty APIs — Device age {% if status.VendorWarranty.Configured %}Configured{% else %}Not configured{% endif %}

A network scan can't tell you how old a device is — BIOS date isn't purchase date. What it can do is pull the BIOS serial number over WinRM (already collectible today) and look that serial up against the manufacturer's warranty API to get ship/purchase date, which is what "age" is actually computed from. Currently alerts on devices ≥ {{ status.VendorWarranty.AgeAlertYears }} years old once populated (configurable).

Request from IT Asset/Procurement (they hold the vendor account relationship):

  • Dell: a TechDirect API account (API key + secret) — registered against your company's Dell account
  • HP: an HP Warranty API key via the HP partner/enterprise portal
  • Lenovo: a Lenovo Warranty API key
  • Outbound HTTPS/443 from the jump server to each vendor's API endpoint (firewall rule)

If your organization already tracks purchase date in an existing asset system/CMDB (like the IT Asset Dashboard export), importing that is usually faster than standing up three vendor API integrations — worth checking before requesting these.

3. MDM — Kiosks (IoT VLAN), fully-managed Android/iOS phones (Wi-Fi) {% if status.Mdm.Configured %}Configured{% else %}Not configured{% endif %}

Kiosks on an isolated IoT VLAN and managed phones on Wi-Fi are typically unreachable from the jump server by design (VLAN segmentation, client isolation) — and even if reachable, they don't run WinRM/SNMP. Their MDM is the only real source of truth for what they are, their OS/app version, and compliance state.

Request from the Endpoint/Mobility/Identity team (pick whichever MDM you actually run):

  • Microsoft Intune: an Azure AD app registration with Tenant ID / Client ID / Client Secret, granted the DeviceManagementManagedDevices.Read.All Graph API permission (admin-consented)
  • Jamf Pro: a Jamf API client (Client ID/Secret) with a read-only device-inventory role, plus your Jamf Pro URL
  • Android Enterprise / Google EMM: an EMM service account key and your Enterprise ID

These are cloud APIs (no firewall path into the IoT/Wi-Fi VLAN needed) — just outbound HTTPS from the jump server to the provider's API endpoint.

4. Cloudflare Zero Trust API — richer WARP device identity (future enhancement) {% if status.CloudflareZeroTrust.Configured %}Configured{% else %}Range-scan only{% endif %}

Today, remote/home users connecting via WARP are already picked up because Discovery scans the WARP-assigned IP range (tagged Cloudflare WARP). The API integration below would add who's connected and from where, straight from Cloudflare, instead of inferring it from a port scan — not built yet, listed here for when you're ready to prioritize it.

Request from your Cloudflare admin:

  • An API Token scoped to Zero Trust (Devices:Read, Access:Read)
  • Your Cloudflare Account ID

Fill in credentials under Integrations in DCAnomalyAgent\Config\settings.psd1, set the relevant Enabled = $true, then click "Refresh status" above.
